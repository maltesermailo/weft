= WEFT Protocol — Specification v0.13 (ULID Identity Edition)
:revnumber: 0.13
:revremark: namespace / role / channel identity → ULID; names become mutable vanity labels
:toc: left
:toclevels: 3
:sectanchors:
:!sectnums:
:attribute-missing: skip

*Fully self-contained; supersedes v0.12. *v0.13 is a wire- and storage-breaking identity change*: namespaces, roles, and channels are now identified by an immutable *ULID*, and their former names become mutable *vanity labels* (<<s5-3,§5.3>>). On the wire a namespace scope is `ns:<ns-id>`, a channel is `#<ns-id>/<chan-id>` (both ULID segments), a top-level channel is `#<chan-id>`, and roles are addressed by role ULID; capability-token and grant scopes embed the same ULIDs, so a rename never re-signs a token or orphans a channel. Clients and the WEFT-IRC gateway (<<s17,§17>>) address by vanity and resolve to the ULID at the wire boundary — examples below show the raw ULID wire form with the vanity in a trailing note. Also new this edition: email-at-registration + typed-code password reset (<<s6-1,§6.1>>). v0.12 added namespace-level membership + `SYNC`; v0.11 was an editorial consolidation. A client can be written from <<s0,§0>>–<<s10,§10>>; a server additionally requires <<s11,§11>>–<<s17,§17>>.*

*WEFT* (working name): a federated chat protocol combining IRC's operational simplicity with Discord's feature semantics. Design goals: small self-host footprint, sovereign networks, explicit consent for every federation act, privacy properties enforced by construction, and a control plane debuggable with netcat.

'''

== 0. Conformance & Terminology

The key words *MUST*, *MUST NOT*, *REQUIRED*, *SHALL*, *SHALL NOT*, *SHOULD*, *SHOULD NOT*, *RECOMMENDED*, *MAY*, and *OPTIONAL* are to be interpreted as in RFC 2119 as clarified by RFC 8174: they carry that meaning only when in ALL CAPITALS.

Recurring terms, defined once:

[cols="1,1",options="header"]
|===
| Term | Meaning

| *namespace root key* | The client-generated Ed25519 key that owns a namespace (<<s2-1,§2.1>>); every role, moderator token, channel policy, and invite chains from it.
| *manifest* | The signed document naming exactly which channels a bridge shares, at what version, with what history/media policy (<<s11-1,§11.1>>); the mutually-acked manifest gates all forwarding.
| *home network* | The single network that mints the ULIDs — and therefore owns the order — for a scope: a channel's namespace-owning network (<<s11-13,§11.13>>), or a group DM's creator network (<<s9-1,§9.1>>, <<s11-12,§11.12>>).
| *spoke* | Any non-home member network of a cross-network channel or group DM; spokes relay posts to the home and mirror its minted order (<<s11-13,§11.13>>, <<s11-12,§11.12>>).
| *compaction* | The post-audit-window rewrite of a channel's stored log into its surviving form: final bodies, per-emoji reaction summaries, tombstones (<<s12-1,§12.1>>).
| *retention hold* | The reporting-placed exemption that keeps an event (and its context) out of both purge and compaction until resolution + grace (<<s12-1,§12.1>>).
| *materialized view* | The compacted wire form batches carry (`HISTORY`/backfill): one `MESSAGE` per surviving message, `REACTIONS` summaries, `DELETED` tombstones — never edit chains (<<s12-1,§12.1>>).
|===

[[s2]]
== 2. Model & Naming

[[s2-1]]
=== 2.1 Entities
* *Network*: a sovereign deployment identified by a DNS name (`test.example`). Owns accounts, hosts namespaces and channels, publishes its signing key, is the abuse-accountable party. *No global state*: nothing leaves a network except through an explicitly agreed bridge manifest.
* *Namespace* (optional): a named channel bundle — the Discord-"server" analog — *created and owned by a user*. At `NS CREATE` a dedicated *namespace root key* is generated client-side and held by the owner; all roles, moderator tokens, channel policies, and invites chain from it. The operator hosts but does not administer; the network key outranks a namespace root *only* for abuse handling (freeze/delete) and rung 3 recovery (<<s2-4,§2.4>>) — it can never silently mint membership or read `e2ee` content. A network with only flat channels never declares a namespace and is fully conformant.
* *Channel*: one home network, optionally inside one namespace — one level, no nesting. Shown by *vanity* here (`#general`, `#gaming/general`); on the wire a channel is identified by ULID, `#<chan-id>` or `#<ns-id>/<chan-id>` (<<s5-3,§5.3>>).
* *Account*: `user@network.tld`, registered and recoverable at the home network.

[[s2-2]]
=== 2.2 Namespace creation & visibility
Creation per network config: `open` (any account, quota default *10*, rate-limited) or `gated` (`ns-create` cap).

[cols="12,34,12,42",options="header"]
|===
| Tier | Directory | Join | Existence disclosure

| `public` | Listed in `DISCOVER` | Open, or invite (ns choice) | Anyone
| `unlisted` | Not listed | Invite required | Invite holders only
| `private` | Not listed | Invite required | *Denied* — indistinguishable from nonexistent
|===

[IMPORTANT]
.Anti-enumeration (normative)
====
"private thing you're not in" MUST be indistinguishable from "does not exist" — same code (`NO-SUCH-TARGET`, <<s8,§8>>), same timing envelope. Covers view-gated channels, expired/foreign msgids, dead invites.
====

[[s2-3]]
=== 2.3 Normalization (normative)
* Machine identifiers: *lowercase ASCII*. Accounts `[a-z0-9-_.=+]{1,64}`; ns/channel segments `[a-z0-9-_]+`; channels ≤200 B incl. `#` and namespace. `=` and `+` exist for *bridge parity* (see decision (3)): a bridged user's account is minted from a foreign identifier, and the account grammar must be wide enough to keep distinct foreign users distinct. `/` is deliberately excluded — it is WEFT's own path separator (`#<ns>/<chan>`, `<origin>/<ulid>`).
* Display strings: UTF-8, NFC on ingest. Raw CR/LF are forbidden inside a line but representable in the *trailing* via the <<s4,§4>> escape table — CR (0x0D) → the two-character sequence `\r`, LF (0x0A) → `\n`, backslash → `\\` — so a message body may be multi-line: it is escaped on serialize and unescaped on parse, never reaching the transport as a raw break. Display names ≤128 B; topics ≤1024 B.

[[s2-4]]
=== 2.4 Namespace recovery (new)

Failure mode addressed: the namespace root key is lost (device loss, owner death, departure) and the community would otherwise be permanently ownerless — plus, at rung 3, the case where the owner is present but is themselves the abuse. Recovery is a *ladder* — each rung louder and more auditable than the last.

All *delayed* rungs share three properties: a *mandatory public delay*, a *mandatory announcement* (`NS-META` event with `recovery=` fields to all members), and *cancellability by the current root* during the window (a live root can always veto — this defeats coerced or hostile recovery). Rung 3 is deliberately *not* a delayed rung: it keeps the announcement, drops the delay and the veto, and compensates with a permanent audit mark (see below). The announcement is the one property every rung shares, so *no rung is ever silent*.

*Rung 1 — Transfer (no delay).* The root signs `NS TRANSFER`. Normal succession; nothing new.

*Rung 2 — Social recovery (7-day delay, RECOMMENDED default).*
* The owner MAY designate a recovery set at any time: `NS RECOVERY SET <name> <m> <key1,key2,...>` — an M-of-N quorum of keys (typically trusted co-admins). Stored in signed ns metadata; members can see that a recovery set exists (not necessarily who).
* Recovery: quorum members co-sign a *rotation record* naming the new root key; any of them submits `NS RECOVER <name> <b64-rotation-record>`. The server verifies M valid signatures from the set, then starts the delay window.
* During the window: `NS-META` announces `recovery=pending;recovery-eta=<ts>;recovery-rung=2` to all members. The current root may cancel with `NS RECOVERY CANCEL <name>` (one signature beats the quorum — the point is that a _live_ owner always wins).
* At expiry the rotation applies: new root key takes over; all tokens chained to the old root expire naturally (short-lived anyway); the rotation is permanently recorded in ns metadata (`root-history`).

*Rung 3 — Operator takeover (no delay).*
* The operator (network signing key) initiates `NS RECOVER` with an operator-signed rotation record. Available whenever the operator judges it necessary — most often _moderation seizure_ of a namespace whose owner is the abuse, and secondarily as the last-resort recovery path when no recovery set is configured or the quorum is unreachable.
* *It applies immediately.* Unlike rungs 1–2 this rung has *no delay window*, and therefore no pending state and nothing to cancel: the two-of-three shared properties above (delay, root-cancellability) deliberately do *not* hold here. Earlier drafts specified a 30-day window; that made the rung unusable for the job it exists to do, because a moderator cannot wait a month and because the veto the window grants would be exercised by exactly the party being removed. See <<appendix-a,Appendix A>> for the amendment and its reasoning.
* *The announcement and the audit mark do hold, and they carry the whole accountability weight.* The rotation is announced (`NS-META`) and is *permanently marked operator-initiated* in `root-history` — auditable by every member and by bridge peers forever. An operator who abuses this pays in visible reputation, which is the honest limit of what protocol can enforce against the party hosting the data.
* What the zero delay removes is the _window_, never the _authorization_: the rotation record MUST still verify against the network signing key. A rotation signed by anyone else is `FORBIDDEN`, as before.

*E2EE caveat (normative):* recovery restores _administration_ — token minting, policy, membership. It NEVER restores `e2ee` history: MLS keys live on member devices, the server holds ciphertext, and a recovered root joins encrypted channels as a fresh MLS member with no access to prior content. Host-blind means host-blind, including from recovery.

*Bridge interaction:* a root rotation is announced to bridge peers via a manifest metadata update; peers re-validate future manifest amendments against the new root. A peer MAY be configured to auto-suspend (not sever) bridges into a namespace during a pending rung-3 recovery.

[[s3]]
== 3. Transport

[[s3-1]]
=== 3.1 QUIC (native)
ALPN `weft/1`. *Stream 0* (bidi): control plane, UTF-8 newline-delimited lines. *Uni streams*: data plane (media, bulk sync). *Datagrams*: voice (WEFT-RT).

[[s3-2]]
=== 3.2 WebSocket fallback
Single WSS connection. Text frames = control lines; binary frames = data plane with a 4-byte virtual stream ID prefix. Voice over WS best-effort; prefer QUIC.

[[s3-3]]
=== 3.3 Session lifecycle
----
open → NEGOTIATING --HELLO/WELCOME--> UNAUTHED --AUTH ok--> READY --QUIT/error--> CLOSED
----
`NEGOTIATING`: only `HELLO`. `UNAUTHED`: only `AUTH`, `REGISTER`, `PING`, `QUIT`. Else `ERR NOT-AUTHED`. Idle pre-auth sessions closed after 30 s (RECOMMENDED).

[[s3-4]]
=== 3.4 Keepalive
`PING [token]` → `PONG [token]` mandatory. RECOMMENDED 10 s interval (matching contemporary chat clients), 2 missed = dead. QUIC keepalive may substitute for sending, not for answering.

[[s3-5]]
=== 3.5 Labeled responses (normative)
Any command MAY carry `label=<opaque ≤64 B>`. Every *direct* response — success event, data page, `ERR` — echoes it; broadcast copies never do. Libraries SHOULD label everything; this is request correlation and the ack foundation (<<s9-2,§9.2>>).

[[s3-6]]
=== 3.6 HELLO
----
C: HELLO weft/1
S: @features=media,backfill,voice,irc-gw WELCOME test.example :Willkommen
----
`features=`: `media`, `voice`, `e2ee`, `backfill`, `irc-gw`, `presence`, `email-required`. Unknown flags ignored. Version mismatch: `ERR UNSUPPORTED`, close.

The negotiation `WELCOME` is sent *before* auth, so its `features=` also let a client shape the login/register form up front: `email-required` (set iff the network runs `require_email`, <<s6-1,§6.1>>) tells the client to collect — and require — an email at `REGISTER`. A network advertises `email-required` only when it also has a mailer configured.

'''

[[s4]]
== 4. Control-Plane Line Grammar

----
@tag1=value;tag2;tag3=value VERB param1 param2 :trailing free text
----
* Limits: line ≤ *32 KiB*; ≤15 middle params; ≤32 tags; tag key ≤64 B (`[a-z0-9./-]+`); unescaped value ≤1024 B.
* Verbs `[A-Z0-9-]+`. *Unknown verbs ignored by servers; unknown events ignored by clients.*
* Middle params: no spaces, no leading `:`. Only trailing (after ` :`) may contain spaces or be empty (empty trailing = empty body, meaningful).
* Tag escaping (the IRCv3 message-tags convention): `;` → `\:`, space → `\s`, CR → `\r`, LF → `\n`, `\` → `\\`; unknown escapes drop the backslash; a dangling backslash is an error.
* *Lenient-in, strict-out*: serializers MUST refuse to emit anything their own parser rejects.
* Oversized payloads → data plane via `STREAM`.

'''

[[s5]]
== 5. Identifiers & Core Types

[[s5-1]]
=== 5.1 Message IDs
`msgid = <origin-network>/<ULID>`. Lexically sortable, timestamp-embedded. Origin-scoped: no bridge collisions; edit/delete authority verifiable. ULIDs assigned *only* by the origin channel actor; actor inbox order = channel total order.

[[s5-2]]
=== 5.2 Retention policies
`ephemeral | retained:<n>(d|h|s) | permanent | e2ee` (n>0).

[cols="1,1",options="header"]
|===
| Mode | Behavior

| `ephemeral` | relay only
| `retained:<dur>` | stored, purged after
| `permanent` | stored indefinitely
| `e2ee` | ciphertext blobs only; server-readable-plaintext *unrepresentable*
|===

Strictest-policy negotiation (bridges): `e2ee` > `ephemeral` > `retained(shorter)` > `retained(longer)` > `permanent`. Policy visible before members speak (`POLICY` on join).

[[s5-3]]
=== 5.3 Namespace, channel & role identity (ULID + vanity)

A namespace, channel, and role are each identified by an immutable *ULID* minted once at creation and *never reused*. The former human name is a mutable *vanity label* — per-network unique, freely renamable, and lockable (an operator reserves a vanity in the web admin panel; a locked vanity can't be registered or changed by a non-operator). Identity is the ULID; the vanity is display and lookup only. This mirrors the account model (<<s10-1,§10.1>>): the ULID is the stable, rename-safe key that capability tokens, grants, channel names, and federation addressing pin, so a rename re-signs nothing and orphans nothing.

*Wire forms.* A `<ns-id>`, `<chan-id>`, and `<role-id>` are bare ULIDs (26-char Crockford base32, no `I`/`L`/`O`/`U`):

[cols="1,2",options="header"]
|===
| On the wire | Meaning

| `ns:<ns-id>` | a namespace scope (was `ns:<name>`)
| `#<ns-id>/<chan-id>` | a namespaced channel — *both* segments ULIDs (was `#<name>/<chan>`)
| `#<chan-id>` | a top-level (namespace-less) channel
| `<role-id>` | a role, in `ROLE` commands/events (was the role name)
| `<network>/<ns-id>` | a namespace across federation — the pinned peer identity (<<s11-10,§11.10>>)
|===

Vanity names never appear as identity on the raw wire. `NS CREATE` / `CHANNEL CREATE` / `ROLE CREATE` submit a *vanity*; the server mints the ULID and returns it (with the vanity echoed in a `vanity=` tag on `NS-META`, and alongside the id-name on channel/role events). Human-facing entry points — DISCOVER, invite links, `FEDERATE <net>/<vanity>`, and the WEFT-IRC gateway (<<s17,§17>>) — accept a vanity and *resolve it to the ULID at the wire boundary*, then pin the id. Clients always display the vanity.

[NOTE]
====
*Example convention.* Because raw ULIDs are unreadable, examples in <<s6,§6>>/<<s7,§7>> use *illustrative placeholder ULIDs* — e.g. `01J8NSGAMING` for the "gaming" namespace, `01J8CHGENERAL` for its `#general` channel, `01J8ROLEMOD` for a "Moderator" role. These are mnemonics, not literal 26-char ULIDs. Where it aids reading, the vanity a client would show is given in a trailing "_(shown as …)_" note. The raw wire carries only the ULID form.
====

'''

== 6. Command Reference

This section (with <<s7,§7>>) is the *client↔server* surface: what a client sends and what it
receives back. The parallel *home↔spoke* (server-to-server) surface is <<s11-14,§11.14>> /
<<s11-15,§11.15>>; it reuses many of these commands and events, since a federated user's
server tunnels the commands here to the home and receives these events back — so an entry may
appear in both references.

Every command accepts a `label` tag (<<s3-5,§3.5>>); the direct response — including `ERR` — echoes it. Each subsection is tagged with its scope: *S*ession · *N*etwork · *NS* namespace · *C* channel · *F* federation/operator. In the tables, the *Cap* column is the required capability (<<s10-4,§10.4>>) — `—` means none — and *→* lists the success event(s) and notable error codes. `|` separates alternatives.

[[s6-1]]
=== 6.1 Session & identity (S/N)

[cols="14,24,10,28,24",options="header"]
|===
| Command | Syntax | Cap | → Result / notes | Example (`→` = direct response)

| `HELLO` | `HELLO <version>` | — | Negotiates the protocol (<<s3-6,§3.6>>). | `HELLO weft/1` → `@features=media,backfill WELCOME test.example :Willkommen`
| `REGISTER` | `REGISTER <account> [<email>] :<password>` | config | Password ≥ 12 B; needs `registration: open` else `FORBIDDEN`. Registration doubles as auth. The optional `<email>` is recorded as a *pending* verification claim (<<s10-5,§10.5>> — verify-later: the account works at once, `VERIFY EMAIL` confirms whenever) and MUST be unique per account. A network with `require_email` set REQUIRES it from native clients — the WEFT-IRC gateway (<<s17,§17>>) is exempt. → `WELCOME` \| `CONFLICT` (name *or* email taken) \| `POLICY` (short password / email required) \| `MALFORMED` (bad email). | `@label=r1 REGISTER ada ada@example.com :correct horse battery staple` → `@label=r1 WELCOME test.example`
| `AUTH PASSWORD` | `AUTH PASSWORD <identifier> :<password>` | — | The `<identifier>` is the account name *or* a registered email (the server resolves it, so a vanity name can change later without breaking sign-in). | `AUTH KEY` | `AUTH KEY <account> <b64-ed25519-pubkey>` | — | Begins device-key challenge-response (flow below). → `CHALLENGE`. | `AUTH KEY ada <b64-pubkey>` → `CHALLENGE <b64-nonce-32B>`
| `AUTH PROOF` | `AUTH PROOF <b64-sig>` | — | Answers the challenge, signing `nonce ‖ network-name`. → `@attestation=<b64> WELCOME` \| `AUTH-FAILED`. | `AUTH PROOF <b64-sig>` → `@attestation=<b64> WELCOME test.example`
| `AUTH ENROLL` | `AUTH ENROLL <b64-pubkey>` | authed | Adds a device to the current account. → `@attestation=<b64> WELCOME`. | `AUTH ENROLL <b64-pubkey>` → `@attestation=<b64> WELCOME test.example`
| `RESET REQUEST` | `RESET REQUEST <email>` | — (UNAUTHED) | Begin password reset: mint + mail a one-time code, but *only* if `<email>` belongs to an account. Valid only before auth. → `RESET-SENT`. | `@label=q RESET REQUEST ada@example.com` → `@label=q RESET-SENT ada@example.com`
| `RESET CONFIRM` | `RESET CONFIRM <email> <code> :<new-password>` | — (UNAUTHED) | Set the new password (≥ 12 B) with the mailed code (short-lived, single-use). | `QUIT` | `QUIT [:reason]` | — | Graceful close. | `QUIT :bye` (connection closes)

| `VERIFY EMAIL` / `BIRTHDAY` | `VERIFY EMAIL <address>` / `VERIFY BIRTHDAY <YYYY-MM-DD>` | authed | Records a verification claim (<<s10-5,§10.5>>): email → `pending` + a mailed one-time code; birthday → self-attested, `confirmed` on the spot. → `VERIFIED`. | `VERIFY EMAIL ada@example.com` → `@state=pending VERIFIED email ada@example.com`

| `VERIFY LIST` | `VERIFY LIST` | authed | The caller's own claims — *owner-only* (subjects are PII, <<s10-5,§10.5>>). → one `VERIFIED` per claim. | `VERIFY LIST` → `@state=confirmed VERIFIED email ada@example.com` (per claim)

Device-key auth is a two-step challenge-response binding a device pubkey to the account; `nonce ‖ network-name` in the signed payload prevents cross-network replay:
----
C: AUTH KEY <account> <b64-ed25519-pubkey>
S: CHALLENGE <b64-nonce-32B>
C: AUTH PROOF <b64-sig(nonce ‖ network-name)>
S: @attestation=<b64> WELCOME test.example
----

[[s6-2]]
=== 6.2 Namespace commands (NS)

Signed NS verbs (`TRANSFER`, `RECOVERY CANCEL`) carry the root signature in a `@sig=<b64>` tag; `NS CREATE` carries the new root pubkey in `@root=<b64>` (<<s2-4,§2.4>>, <<s10-4,§10.4>>). A namespace is addressed on the wire by its *ULID* `<ns-id>` (<<s5-3,§5.3>>); only `NS CREATE` takes a *vanity* (the server mints the id). Human entry points (DISCOVER, invites, the IRC gateway) resolve a vanity to `<ns-id>` at the wire boundary. Examples use the placeholder id `01J8NSGAMING` _(shown as `gaming`)_.

[cols="14,24,10,28,24",options="header"]
|===
| Command | Syntax | Cap | → Result / notes | Example (`→` = direct response)

| `NS CREATE` | `NS CREATE <vanity> [public\|unlisted\|private]` | none (`open`+quota) / `ns-create` (`gated`) | Default `unlisted`. Takes the desired *vanity*; the server mints the namespace ULID and returns it. Client generates the namespace *root key*, submits its pubkey (recorded as delegation root). The `NS RECOVER` rungs in brief (normative text: <<s2-4,§2.4>>): a quorum-signed rotation record starts the 7-day rung-2 window (announced, root-cancellable); a network-key-signed record is rung 3 and *applies immediately* — no window, no pending state — permanently marked operator-initiated in `root-history`.

*Channel layout & server-authoritative categories (extension).*

* Channels carry a `category` (free label) and `position` (integer), set via `CHANNEL META` (<<s6-3,§6.3>>).
* `CHANNELS <ns-id>` returns the ordered layout as `CHANNEL-LAYOUT` events, sorted by (category, position, vanity), *led by the namespace's `NS-META`* — so a client renders every group, including empty categories, purely from server state.
* The category _list_ itself lives on the namespace: `NS META <ns-id> categories :<comma-list>`, echoed in NS-META's `cats=` tag.
* A `category`/`position` change *broadcasts `CHANNEL-LAYOUT`* to the channel's members — re-ordering reaches every client, not just the mover. Clients keep no category state of their own.
* Private-namespace layouts are view-gated (invariant 1).

*Membership is durable (normative).* Under v0.12 membership is *namespace-level*: `NS JOIN` records one `(account, namespace)` row and a channel's access is *derived* — `member(ns) ∧ can-view ∧ ¬hidden` — never a stored per-channel row. A `PART <#ns-id/chan-id>` sets a per-account *hide override* (`hide_override(account, channel)`); `JOIN <#ns-id/chan-id>` clears it; `NS LEAVE` drops the ns row and every hide override for it. **Top-level channels (no namespace) keep the per-channel `(account, channel)` membership unchanged** — the flat/IRC deployment mode is untouched, and a `CHANNEL`-scope ban still force-parts + clears it. A channel *created* in a namespace is in every ns member's derived set immediately, with no membership writes. On auth the server auto-rejoins the account to its *derived* channel set, so channels reappear on reconnect with no client-side re-join (v0.12: also pullable via `SYNC`, <<s6-9,§6.9>>). Join/part announcements *dedupe by account* — a second device broadcasts no fresh `MEMBER`, and counts are distinct-account counts.

*Presence vs. membership (Discord-style).* The roster is the _persistent_ membership; online-ness is "holds a live session in the channel". A *disconnect* broadcasts `PRESENCE <user> offline` (membership retained) — only an explicit `PART`/kick/ban emits `MEMBER … part` (roster removal); a reconnect of an existing member broadcasts `PRESENCE <user> online`, not a fresh join. The presence map is live-only (<<s6-1,§6.1>>: never stored, never bridged); a live `invisible` member reads `offline`.

*Unread counts are pushed, not only polled.* A per-channel `UNREAD-COUNTS` follows each `MARKED` in the login snapshot (<<s9-7,§9.7>>), and a fresh count rides the cross-device `MARK` sync to the account's _other_ sessions — so badges survive reload/reconnect and stay consistent across devices. What is counted:

* `unread` — real root messages from _other_ senders; own messages and join/part system rows are excluded.
* `mentions` — the subset referencing the account (`@account`), `@everyone`/`@here`, or a *pingable* role the account holds (a role with `pingable=1`, `@`-mentioned by name); a body-text heuristic — there is no structured mention field. An `@everyone`/`@here` ping is a privileged act gated by the `ping-everyone` capability at the scope; a role is pingable only while its definition carries `pingable=1`. Both flags are the notification gate — a role that is not pingable, or an `@everyone` from a sender lacking `ping-everyone`, still renders as text but raises no mention.

Invite tokens are capability tokens with an *unbound subject*: one object serves single-use / expiring / vanity links — offline-verifiable authorization, never itself a membership credential.

[[s6-5-1]]
==== 6.5.1 Roles — named capability-token bundles

A *role* is a named, colored bundle of capability tokens at a scope — `(scope, name, color, caps)` — giving clients human-readable labels over <<s10-4,§10.4>> capabilities. Three rules define the model:

* *Enforcement stays purely token-based.* Assigning a role grants exactly its `caps` as ordinary tokens; every permission check is a pure capability-token check — no role tables in the _enforcement_ path.
* *Membership is explicit, never derived.* An account wears a role because it was _assigned_ (`ROLE ASSIGN` / `ROLE UNASSIGN`, recorded server-side) — never because its caps happen to be a superset of the bundle. Deriving membership from caps was rejected: it wrongly marks owners/operators (who hold every cap implicitly) as wearing every role, and can't distinguish a coincidental cap match from an intended assignment.
* *The assignment record is display metadata.* It drives rendering and propagation; it is never consulted for a permission decision.

The `ROLE` event carries a definition (keyed by its role ULID); the `ROLE-MEMBER` event carries an account's explicit assignments (comma-separated role ids). Clients render pills from the intersection, showing each role's current display name.

*Role identity is a ULID (<<s5-3,§5.3>>).* A role is `(id, scope, name, color, caps)`; the `id` is minted at `ROLE CREATE` and immutable, the `name` is a mutable display label. `ROLE UPDATE`/`DELETE`/`ASSIGN`/`UNASSIGN`/`REORDER` all address the role **by id**, so:

* *Rename is free.* `ROLE UPDATE` with a new `:<name>` changes only the label — identity (and thus every assignment + granted token) is unchanged, so there is no server-side migration (the pre-v0.13 `ROLE RENAME` that carried definition + assignments is gone, folded into `UPDATE`).
* Already-granted tokens need no migration: a role's authority is its `caps`, which an update leaves untouched unless the caps themselves are edited (`ROLE DELETE` likewise leaves granted tokens alone — revoke separately).
* The cap check precedes any existence probe (invariant 4), so no role command can be used to enumerate roles.

*Role channel-permissions.* A namespace role and a channel role that share the *same display name* compose to give the Discord "role X has permission Y _in channel Z_" override, without a rules engine:

* A role named `Speaker` at `ns:01J8NSGAMING` carries namespace-wide caps; a role named `Speaker` at `#01J8NSGAMING/01J8CHSTAGE` carries caps _for that channel only_.
* Assigning the namespace role grants both: `ROLE ASSIGN ns:01J8NSGAMING <account> <ns-role-id>` grants the namespace bundle *and* every same-named channel role's caps on that namespace's channels.
* Editing a channel role re-grants it to every current member of the namespace role *immediately* (through the membership records) — so a newly-added channel permission reaches existing holders with no re-assignment.

Enforcement stays token-based (<<s10-4,§10.4>>): a namespace scope covers its channels; a channel scope covers only itself.

*Who can be moderated.* `<member>` is a **member reference**: a bare `<account>`
for one of this network's own, or `<account>@<network>` for a member who is not —
a federated peer's user, or a **bridged** one — a Matrix member of a projected or
consumed namespace, who is modeled as a user of the realm's network
(<<s11-4,§11.4>>). Namespace rosters have always held both
forms; the moderation verbs took a bare account only, which made a bridged member
unmoderatable by construction. They are not a separate class of participant, and a
moderator's reach is the room, not the passport.

Two consequences follow from the deny-list being *ours*:

* It is enforced where their traffic **enters** — a muted or banned bridged member's
  relayed messages are refused on ingest, exactly as a NETBLOCKed network's are
  (<<s11-6,§11.6>>). This holds whether or not the bridge is reachable.
* A server SHOULD also relay the act outward so the foreign system applies it
  (removing them from the room). That relay MAY fail — the home is not an authority
  in someone else's realm — and its failure MUST NOT undo the local deny. A
  moderator's decision does not depend on a bridge being up.

*How posting permission composes.* A message is allowed only when all three of these hold:

----
can_post  =  not muted   AND   not banned   AND   (channel is open   OR   sender holds `send`)
----

Two independent surfaces feed that check:

* *Deny-list (mute / ban)* — per-account blocks keyed by `(scope, account)`. A block applies to a channel if its scope _covers_ that channel: the channel itself (`#ns-id/chan-id`), its namespace (`ns:<ns-id>`), or the whole network (`*`). That covering rule is also _who moderates what_ — a `*` block is set by network moderators, `ns:` by namespace moderators, `#ns-id/chan-id` by channel moderators.
* *Restricted posting* — `CHANNEL META <#ns-id/chan-id> posting :restricted` flips a channel from open to send-gated. Posting then requires the `send` capability, so `GRANT send` / `REVOKE send` (+ epoch, <<s10-4,§10.4>>) decides who may speak — e.g. an announcements channel.

A *mute always denies*, whatever the posting mode. Kick and ban broadcast a `MEMBER … part` so the target sees the removal; the acting moderator gets a `MODERATED <scope> <member> <mute|unmute|ban|unban|kick>` echo (`by=`/`reason=` tags).

*`REPORT` arguments.*

[cols="24,34,42",options="header"]
|===
| Argument | Values | Notes

| `category` | `spam` · `harassment` · `violence` · `sexual` · `csam` · `illegal` · `self-harm` · `other` | Normative set; extensible with an `x-` prefix.
| `scope` | `ns` (default) \| `net` | Routing hint: namespace moderators vs. the network operator. `csam` and `illegal` are ALWAYS _also_ routed to `net` — the legally accountable party.
| `note` | free text | Optional, ≤ 1024 B.
|===

You can only report what you can see: reporting is membership-gated, and an invisible or absent msgid returns `NO-SUCH-TARGET` (anti-enumeration unchanged). Handlers are the holders of the `reports` cap at the concrete scope (`ns:<ns-id>` or `*`).

*Where a report lands:*

* `ns`-scope on a namespaced channel → the namespace owner;
* `ns`-scope on a top-level channel or a DM → the operators;
* `net`-scope → the operators;
* `csam` / `illegal` → *also* the operators, always.

[NOTE]
.Honest limitation
====
the live `REPORT-FILED` push reaches a queue's _default_ handlers (ns owner / operators); delegated `reports`-cap holders fetch via `REPORTS LIST` — pull, not push.
====

*`REPORTS RESOLVE` actions:* `dismissed` · `content-removed` · `user-actioned` · `escalated`.

* `escalated` re-routes an ns-scope report up to net scope — the report stays open, holds intact.
* Handlers receive the full `REPORT-RESOLVED` (`by=`, `note=`); the reporter receives the minimal form — no handler identity, no note.

*Content states* (marked honestly on the filed report):

[cols="1,1",options="header"]
|===
| State | Meaning

| `verified` | The server still holds the reported event; a *retention hold* is placed (<<s12-1,§12.1>>).
| `unverified` | The msgid is expired or the channel is `ephemeral` — nothing server-side confirms the content. Accepted and flagged; handlers weigh it accordingly.
| `reporter-attested` | `e2ee` channel: the server holds only ciphertext. The reporter MAY voluntarily attach the plaintext they saw (marked reporter-provided, not server-verified). The alternative — server-readable "reportable e2ee" — would break <<s14,§14>>'s unrepresentability guarantee and is rejected.
|===

*Confidentiality.* The reported party is never notified and MUST NOT learn the reporter's identity from any protocol surface. Handlers see the reporter's account (accountability against report-flooding); a network MAY anonymize the reporter toward ns-scope handlers while preserving it for the operator.

[[s6-9]]
=== 6.9 Synchronization (SYNC) — v0.12

`SYNC` is a one-shot client state sync that replaces the startup DISCOVER + CHANNELS-per-ns + HISTORY-per-channel loop. It has two forms, distinguished by the presence of a cursor:

[cols="14,24,10,28,24",options="header"]
|===
| Command | Syntax | Cap | → Result / notes | Example

| `SYNC` (fresh) | `SYNC [preview=<n>]` | authed | No cursor = fresh login. Emits the inline *skeleton* — per namespace the account belongs to: `NS-META`, then per *visible* channel `CHANNEL-LAYOUT` + `POLICY` + (`MARKED` + `UNREAD-COUNTS` where a read marker exists); plus top-level channels and `FRIEND`/`GROUP` rows — terminated by `@cursor=<token> SYNC END`. `preview=0` = skeleton only. | `@label=s SYNC preview=0` → `NS-META …` + `CHANNEL-LAYOUT …` + `POLICY …` + … + `@cursor=<token>;label=s SYNC END`
| `SYNC` (delta) | `SYNC since=<cursor> [preview=<n>]` | authed | Serves every row with `seq > cursor` in the account's visible set, as *materialized* upsert rows (final `MESSAGE` + `REACTIONS` + `DELETED` — never event chains), then `SYNC END` with a fresh cursor. Catches offline *mutations of old messages* that ULID paging misses. A cursor whose epoch ≠ the server's current epoch is treated as cursor-less (full resync). | `@label=s2 SYNC since=<token>` → `MESSAGE …` + `REACTIONS …` + `@cursor=<token>;label=s2 SYNC END`
|===

*The cursor is opaque (normative).* A ≤64-byte token (same convention as `label` and the `MORE` cursor); the client stores it per device and echoes it verbatim, never parsing it. Internally it encodes `epoch:seq` — a server-global monotonic *modification sequence* (`seq`, stamped on every insert *and update* of a client-visible row) prefixed by a *sync epoch* (IMAP UIDVALIDITY, server-wide). The epoch is bumped on any restore-from-backup / storage rebuild that could re-issue seqs, so a stale-epoch `since=` cleanly forces a full resync instead of silently losing rows. The cursor a client receives is the *low-water mark* of committed seqs — never past an uncommitted lower seq.

*Apply rule (normative).* A delta row whose key the client already has *replaces* it (upsert; keys: message → msgid, reaction summary → (msgid, emoji), meta → (target, key), marker → channel). Order-insensitive and idempotent. Purge is signalled by watermark, not tombstones: retention-purged rows produce no delta entry.

*Previews (normative).* Message previews are a server-side optimization the server MAY withhold per channel; a conforming client MUST load a preview-less channel on demand via `HISTORY`. When served, previews and the per-channel `CHANSYNC` header ride a data-plane body stream handed off by `SYNC BODY <token>` in place of the inline `SYNC END` (<<s7-9,§7.9>>).

*Delta horizon (RECOMMENDED).* The server need not retain change history forever; it serves deltas for cursors up to `max(retention window, 30 d)` old, and emits a per-channel `CHANSYNC … reset` (client drops its cached rows) for an older cursor, a newly-visible channel, or a re-keyed channel.

'''

== 7. Events Reference

Events are the server→client half of the protocol; a client *MUST ignore any event it does not recognize* (forward-compat, <<s4,§4>>). Events are grouped below by concern. The *Example* column is a concrete wire line; `…` between lines abbreviates omitted events. A _direct_ response echoes the request `label` (<<s3-5,§3.5>>) — shown where relevant; _broadcast_ copies never do.

*Key=value convention (normative).* _Commands_ carry optional `key=value` pairs as *middle params*, shown in their Syntax (`HISTORY limit=`, `GRANT expiry=`, `INVITE MINT max-uses=`, `ROLE CREATE hoist=`). _Events_ carry them as *tags* (`@key=value`, before the verb, <<s4,§4>>) — every `key=` in a Payload/tags column below is a tag unless it appears in the event's Syntax as a middle param. The sole event-side exception is `ROLE`, whose `hoist=`/`pingable=`/`pos=` echo the command's middle-param form.

[[s9]]
== 9. Semantics & Guarantees

[[s9-0]]
=== 9.0 Protocol invariants (normative)

The document cites these by number ("invariant N"). Each is normative wherever the surface it names exists, and each is meant to be enforced *as a test*, not just as code. Numbers 5–7 are cited nowhere in this document and are left `[reserved]` rather than reconstructed.

[cols="6,18,76",options="header"]
|===
| # | Invariant | Statement

| 1 | *Anti-enumeration* | "A private thing you're not in" MUST be indistinguishable from "does not exist": one code (`NO-SUCH-TARGET`, <<s8,§8>>), one timing envelope — covering nonexistent, private, view-gated, expired/foreign msgids, and dead invites (<<s2-2,§2.2>>). The same uniformity extends to the data plane: a bad media bearer, a non-member fetch, an absent blob, and a spent backfill token are one not-found (<<s13,§13>>, <<s11-7,§11.7>>). *This applies inside the membership boundary too* (v0.12): a namespace member without `view` on a gated channel observes nothing — no `CHANNEL-LAYOUT` row, no sync section, `NO-SUCH-TARGET` on a probe, and absent from the derived roster (<<s6-3,§6.3>>). The presence of hidden things never leaks.
| 2 | *Origin authority* | A message belongs to its origin: `msgid = <origin>/<ULID>` (<<s5-1,§5.1>>). Bridged events keep their origin msgids (never re-minted); events on a bridge are accepted only when `msgid` origin = the authenticated peer. For a channel the origin is its *home* (<<s11-12,§11.12>>): the home is the sole minter and enforces `EDIT`/`DELETE` by *authored-by* (the `@as` command vouches the actor), while spoke replicas honor only home-origin events (`FORBIDDEN origin` elsewhere) (<<s11-4,§11.4>>). Backfilled events are verified exactly like live traffic (<<s11-7,§11.7>>).
| 3 | *Forwarding gate* | A channel is forwardable to a peer iff it appears in *both* the last mutually-acked manifest snapshot and the current one; the same gate applies to ingestion and to backfill (<<s11-1,§11.1>>, <<s11-7,§11.7>>). Forwarding outside it is a protocol violation, not a soft failure.
| 4 | *Caps before effects* | Capability checks precede side effects — and precede existence probes, so a permission check can never be used to enumerate hidden things (<<s10-4,§10.4>>; e.g. the <<s6-5-1,§6.5.1>> `ROLE RENAME` error order).
| 5–7 | _[reserved — recover from repo history or retire]_ | Not cited in this document.
| 8 | *E2EE host-blindness survives everything* | Server-readable plaintext for an `e2ee` channel is _unrepresentable_ (<<s5-2,§5.2>>, <<s14,§14>>): no server search, embeds, thumbnails, or compaction — and recovery (<<s2-4,§2.4>>) restores administration, never history.
| 9 | *No silent root rotation* | Every namespace root rotation is announced (`NS-META`); delayed rungs add a mandatory public window and a current-root veto; rung 3 drops the window but is network-key-authorized and permanently audit-marked operator-initiated in `root-history` (<<s2-4,§2.4>>).
| 10 | *Sync is upsert* | Every non-live fetch (`SYNC`, `HISTORY`, federated backfill) serves *materialized current state* keyed for replacement; event chains (`EDITED`, reaction add/remove) never appear off the live path, and a client applies a delta row by *replacing* the row it already holds by key (<<s6-9,§6.9>>, <<s12-1,§12.1>>).
| 11 | *Holds outrank retention* | Reported content and its context are exempt from purge *and* compaction until resolution plus grace; holds are invisible on every protocol surface and travel with their content (e.g. across a channel rename) (<<s12-1,§12.1>>, <<s6-3,§6.3>>).
| 12 | *Reporter confidentiality* | The reported party never learns the reporter's identity from any protocol surface; bridge-forwarded reports strip it by default (<<s6-7,§6.7>>, <<s11-9,§11.9>>).
| 13 | *SSRF classifier guard* | Every server-side fetch of a user-influenced URL (auto-federation dial + well-known fetch, unfurl proxy) MUST classify every resolved address before connecting and refuse non-public targets; testable as a pure classifier (<<s11-10,§11.10>>, <<s13,§13>>).

[[s9-1]]
=== 9.1 Ordering
Per-channel *total order* = the *home actor's* ULID order; bridged replicas preserve it. A channel's *home* is the network that owns its namespace, and that network is the *sole ULID writer* for the channel (<<s11-13,§11.13>>) — exactly as a group DM's home is its creator's network (<<s11-12,§11.12>>). Remote members' posts are relayed to the home to be minted into the one order; they are never minted independently by a spoke. No cross-channel guarantees. DMs: total order per (network, pair).

[[s9-2]]
=== 9.2 Delivery & acks
* *Send:* `MSG` + `label` → the echoed `MESSAGE` (same label, assigned msgid) _is_ the ack. No echo → resend with the *same* label; servers dedup `(session, label)` for 5 minutes → effectively exactly-once.
* *Receive:* dedup by msgid.
* *Backpressure:* a lagging client gets `SLOW` + a forced HISTORY resync; never unbounded buffering.

[[s9-3]]
=== 9.3 Message model (event sourcing)
Edits/deletes/reactions are new events referencing the original msgid — never in-place mutation — *on the live path*; storage and batches use the compacted materialization (<<s12-1,§12.1>>). Replies: `reply-to=`. *Threads are views, not channels*: `thread=` tag, no separate membership, `HISTORY thread=` filter.

[[s9-4]]
=== 9.4 Rich content
UTF-8, optional `fmt=md` (CommonMark subset); oversize → `TOO-LARGE`, never truncation. Link embeds are server-generated sub-events — clients never implicitly fetch third-party URLs (the server-side unfurl proxy, <<s13,§13>>, exists for exactly this reason).

*Threads* are views, not channels (<<s9-3,§9.3>>):

* A reply is an ordinary channel `MESSAGE` carrying `thread=<root>` — it broadcasts to the channel like any message, so every member and bridge sees it; clients MAY hide replies from the main timeline (an "N replies" indicator) as presentation.
* `HISTORY <#ns-id/chan-id> thread=<root>` returns just the thread (root + replies, oldest-first).
* A thread may carry an optional *display name* — metadata keyed by the root msgid, never a new identity — set/cleared via `THREAD NAME`, listed via `THREADS` (<<s6-4,§6.4>>); naming is authorized by the same rule as posting (`can_post`, <<s6-7,§6.7>>).

*Custom emoji* are per-namespace (`EMOJI ADD/REMOVE/LIST`, <<s6-2,§6.2>>): clients render `:name:` as an inline image in bodies *and reactions* — a custom-emoji reaction's key is the literal `:name:` string, so the reaction model is unchanged.

[[s9-5]]
=== 9.5 DMs (v1)
`MSG @user`, same network only; network-config retention (default `permanent`); both accounts, all devices; `HISTORY @user` symmetric; edits/deletes/reactions/replies yes, threads no.

*Cross-network note (honest).* True 1:1 cross-network DMs remain deferred (<<s18,§18>> #7: consent + routing without a channel manifest). In practice, a *two-member cross-network group DM* (<<s6-8,§6.8>>, <<s11-12,§11.12>>) already carries the conversation — a home-authoritative group is the current cross-network path. What stays deferred is the 1:1 DM _semantics_: the default-`permanent` retention rule, the symmetric `HISTORY @user` surface, and the no-threads rule above are specified for same-network DMs only.

[[s9-6]]
=== 9.6 Time
Server-stamped via ULIDs; client clocks untrusted.

[[s9-7]]
=== 9.7 Client reconnect (RECOMMENDED)
v0.12 collapses reconnect (and fresh login) to one code path:

. Reconnect with jittered backoff (1 → 60 s), then `HELLO` → `AUTH KEY`.
. `SYNC since=<stored cursor>` — the server replays every row changed since the cursor as materialized upsert rows, in one pass, and returns a fresh cursor on `SYNC END` (<<s6-9,§6.9>>). Fresh login is the same verb with no cursor (full skeleton). This *replaces* the old per-channel `HISTORY after=` catch-up loop, which structurally missed offline mutations of old messages.
. Resend unacked labels (<<s9-2,§9.2>> dedup makes this safe).

The skeleton's `MARKED` + `UNREAD-COUNTS` rows restore read state, so badges survive the reconnect. (For backward compatibility the server may still auto-replay `MEMBER`/`POLICY` on auth for clients — e.g. the IRC gateway — that do not issue `SYNC`.)

[[s10]]
== 10. Identity

[[s10-1]]
=== 10.1 Account
`user@network.tld`; home network handles registration, recovery, moderation accountability.

Each account also has an immutable *ULID*, minted at registration and never
reused. The handle is the login + display name; the *ULID is the stable identity
capabilities key by* (<<s10-4,§10.4>>) — so grants survive a (future) rename and a
re-registered handle never inherits stale authority. The ULID is a per-network
identifier (like the handle): unique within its network, meaningful only relative
to it. It is internal — never shown; the user-facing identity stays
`user@network`.

[[s10-2]]
=== 10.2 Portable keypair attestation
Ed25519 device keys; home network signs `{pubkey, account, network, expiry, sig}` (deterministic CBOR encode-before-sign); verified remotely via `https://<network>/.well-known/weft` (cached). No global identity server. Rotation = superseding attestation; revocation via well-known. Key rotation never evades NETBLOCK (name-keyed).

Well-known document (JSON):
[source,json]
----
{ "protocol": "weft/1", "network": "test.example", "signing-key": "<b64-ed25519-pubkey>" }
----

[[s10-3]]
=== 10.3 Display identity
Signed profile blob (nick, avatar) travels with the user; remotes MAY override display, MUST show canonical `user@network`. A profile also carries two optional free-text fields set by its owner and broadcast to co-members: a *bio* (`PROFILE SET @about=`, ≤512 B, shown on the full profile view) and a *custom status* (`PROFILE SET @status=`, ≤128 B, a short one-liner shown inline in member lists and on the profile card). Both use the same partial-update rule as the display name — a present tag sets (empty value clears), an absent tag leaves the field unchanged. Neither is part of the signed profile blob yet (M-prof-5), so both are stored and shown on their home network only — a bridged profile drops them.

*Server nicknames.* A member MAY carry a *per-namespace* display name (`NICK <scope> <account> :<nick>`, ≤128 B, empty clears), which overrides the global display name for that member within that namespace only. Setting your OWN requires the `nick` capability at the scope; setting another member's requires `manage-nicks` (moderator). Changes broadcast as `NICK` events; a client pulls the current set with `NICKS <scope>`. Home-network only for now (nicknames aren't in the signed blob).

[[s10-4]]
=== 10.4 Capability tokens
----
token = sign(issuer_key, {              // deterministic-CBOR body, version 2
  subject: <pubkey | account-ULID | account@network> | UNBOUND,
  scope:   <#ns-id/chan-id> | ns:<ns-id> | *,   // ULIDs (§5.3) — rename-safe
  caps:    [...],
  expiry:  <short>,
  chain:   [parent hashes]   // to the scope root
})
----
The *subject* is one of: a device *pubkey* (device-bound); a *local
account's ULID* (<<s10-1,§10.1>> — never the mutable handle); a *foreign
`account@network`* (a federated user granted authority on this network — F owns
her ULID, which this network neither knows nor keys on, so it names her by the
network-qualified handle, <<s11,§11>> homeserver authority); or *UNBOUND* (an invite,
bound to the redeemer's key on redemption). Only a *pubkey* subject may sign
child tokens (delegate); account/foreign/unbound subjects are leaves. The body is
*version-tagged*: v1 (name-subject) tokens are refused on sight — an upgrade
re-grants.

* *Encoding:* deterministic CBOR, encode-before-sign (Biscuit is a possible future upgrade).
* *Scope is ULID-keyed (v0.13, <<s5-3,§5.3>>):* the `scope` string embeds the namespace / channel *ULID* (`ns:<ns-id>`, `#<ns-id>/<chan-id>`), never the mutable vanity — so renaming a namespace or channel re-signs nothing and no grant is orphaned. A pre-v0.13 name-scope token is inert (nothing is named `ns:<name>` any more); the grant records re-key in the store migration and tokens re-mint on next `GRANT`/auth. `covers` is ULID equality.
* *Delegation:* via `grant:X`; chains verify up to the namespace root key or the network key.
* *Roles* (<<s6-5-1,§6.5.1>>) are named token templates; editing a role re-mints on refresh. A role's holder may be a *foreign `account@network`* — membership and granted caps key by that subject, so a partner network's user can wear a role here (<<s6-5,§6.5>>).
* *Revocation:* short expiry + refresh (`TOKEN` events) + per-scope revocation epochs.
* *Standard capability set:* `send`, `edit-own`, `delete-own`, `delete-any`, `react`, `pin`, `invite`, `nick`, `manage-nicks`, `ping-everyone`, `kick`, `ban`, `mute`, `policy`, `view`, `attach`, `chan-create`, `reports`, `bridge`, `ns-admin`, `ns-create`, `netblock`, `media-block`, `grant:<cap>`. (`nick` = set your own per-namespace display name; `manage-nicks` = set any member's, <<s10-3,§10.3>>; `ping-everyone` = fire an `@everyone`/`@here` scope-wide ping, <<s6-3,§6.3>>.)
* *Implicit `@everyone` role:* a reserved namespace role every member holds without an explicit assignment — its caps are the namespace's baseline permissions (Discord's `@everyone`). Edited like any role but never assigned, reordered or deleted; resolved live for members alongside grants. A *channel*-scoped `everyone` role is honored the same way as a **per-channel** baseline layered over the namespace one (both are resolved live for members at a channel scope) — this is the channel-permission editor's `@everyone` target.
* *Scope floors:* `netblock` / `media-block` at `*` only; `reports` grantable at `ns:` and `*`; `mute`/`ban`/`kick` at `#ns-id/chan-id`/`ns:`/`*` — the moderation tiers (<<s6-7,§6.7>>).
* View gating gets full anti-enumeration (invariant 1). *Capability checks precede side effects, always* (invariant 4).

[[s10-5]]
=== 10.5 Account verification (email / age)

Accounts carry *verification claims* — `(kind, subject, state)` where `kind` is an open namespace (`email`, `birthday`, …), `subject` is what's claimed (an address, a birth date), and `state` is `pending` | `confirmed`. Two proof models:

* *Server-proven (`email`):* `VERIFY EMAIL <address>` records a `pending` claim and mails a one-time code; `VERIFY CONFIRM email <code>` proves it (`confirmed`). The code is short-lived (15 min), single-use, in-memory (a restart just means re-request).
* *Self-attested (`birthday`):* `VERIFY BIRTHDAY <YYYY-MM-DD>` records + `confirms` on the spot — honestly self-declared, not server-proven (a server cannot verify age without an ID provider, <<s18,§18>>).

`VERIFY LIST` returns the caller's own claims (one `VERIFIED <kind> <subject>` per claim, `@state=`). *Subjects are PII* (email address, birth date) → returned *only to the owner's own session*, never broadcast. This is *badge-only*: claims do not gate channel/cap access yet (an age-gate is a later policy extension). Mail delivery is a deployment concern; a server with no mailer configured still records the claim (a development server may surface the code out-of-band).

[[s11]]
== 11. Federation — Scoped Bridging

*At a glance.* Two networks share *one* authenticated bridge session (<<s11-2,§11.2>> — `AUTH BRIDGE`, ALPN `weft/1` over QUIC stream 0 or WS). Over it they exchange just two kinds of message — *commands* up and *events* down (<<s11-11,§11.11>>); media rides two _separate_ planes. A user acts on the home by tagging a command `@as=<account>`; the effect returns as an event (the labelled event is the ack, <<s3-5,§3.5>>):

----
       NETWORK  S  (a spoke for #ns/chan)                     NETWORK  H  (its home)
  ┌─ one bridge session — AUTH BRIDGE (each proves its network key) ──────────────────
  │
  │  manifest control   ◄──── PROPOSE / ACCEPT / REQUEST / ADD / REMOVE / SEVER ───►   §11.1
  │  (symmetric)              (+ MANIFEST announced to members)
  │
  │  user commands      ───── @as=<account> <§6 verb>  (MSG/EDIT/HISTORY/GRANT/…) ──►  §11.11
  │  (homeserver auth)        content mints home-authoritatively; enforced vs H's grants
  │
  │  events (the return)◄──── §7 events, home-origin, one hop ────────────────────     §11.4
  │  (home → audience)        MESSAGE / EDITED / DELETED / REACTION / TOKEN / …
  │                           the labelled ack rides the copy to the poster's network
  │
  │  group membership   ◄──── GROUP-ROSTER (event) · GROUP CALL/ROSTER (voice) ────    §11.12
  │  history backfill   ───── HISTORY ──►   ◄── BATCH / STREAM (network-level pull)     §11.7
  │  report forwarding  ───── REPORT-FORWARD  (reporter stripped) ────────────────►    §11.9
  └───────────────────────────────────────────────────────────────────────────────────
  ══════════════════════ separate data / media planes ════════════════════════════════
     media mirror        ───── MIRROR <hash> (self-auth) ──► pull                      §11.8
     voice relay         ◄═══════════ audio (LiveKit cascade) ═══════►                 §16
----

The manifest, media, and voice channels are *symmetric* (either peer initiates for its own
scopes); *content* is *home-authoritative* — a channel's or group's home mints and fans out,
spokes relay to it with `@as` commands (<<s11-12,§11.12>>). Roles are per-scope: a network is
the home of the namespaces it owns and a spoke for the rest.

[[s11-1]]
=== 11.1 The manifest
----
manifest = sign(scope_authority_key, {
  peer, version (monotonic), channels: [...],
  history: from-epoch | full,
  media:   mirror | mirror-max:<bytes> | none,
  typing:  yes | no,
  created, updated
})
----
Both sides store manifest + peer ack; *forwarding outside the last mutually-acked version is a protocol violation*. Scope proposals compile a *snapshot*; later channels need explicit `BRIDGE ADD`. No surprise forwarding.

[[s11-2]]
=== 11.2 Bridge sessions

A bridge session is opened with *`AUTH BRIDGE <peer-network> <b64-network-pubkey>`* on the same acceptor path as clients: the peer asserts its network signing key and proves control via the <<s6-1,§6.1>> `CHALLENGE`/`AUTH PROOF` flow (signing `nonce ‖ our-network`). Success yields a *bridge session, not an account session*, bound to the proven key — manifests received on it verify against that key.

Two configurable trust modes: *pinned* (default/closed) accepts only configured peers whose asserted key matches the pin; *accept-any* (open federation) accepts any non-blocked network on the key it proves control of — trust-on-first-use, with `NETBLOCK` (<<s11-6,§11.6>>) as the escape hatch. A pin always wins over accept-any. Every failure funnels to the uniform `AUTH-FAILED` (no peer-existence oracle).

The `bridge` _capability_ plays no role in session authentication — it is the <<s11-3,§11.3>> authorization to *propose* channel-scope manifests.

[[s11-3]]
=== 11.3 Authorization ladder
Proposing a manifest requires authority proportional to its blast radius: a single channel (`#ns-id/chan-id`) needs a `bridge` capability holder; an `ns:<ns-id>` scope needs the namespace root; a `*` (whole-network) scope needs the network signing key itself. The wider the scope a bridge shares, the stronger the signature that must stand behind it — blast radius is priced in signatures. The ladder is enforced _locally_ on the proposing side; the wire manifest is uniformly *network-key-signed*, so the peer verifies it against the signer's well-known key.

[[s11-4]]
=== 11.4 Event flow
Origin msgids + attestations intact, verified against the origin's well-known key. *A channel's origin is its home* (the namespace owner's network, <<s11-12,§11.12>>): the home mints every message into one total order and is the single point that fans it out one hop to each spoke. A remote member's post reaches the home as an `@as MSG` command (<<s11-12,§11.12>>), not the mirror; the mirror then carries the home-minted event. Because the home is the origin, a home→spoke copy is *one hop from origin* — this is what lets a channel with members on three or more networks deliver every message to everyone (a non-home spoke's post could otherwise never reach a second spoke without the forbidden transitivity). EDIT/DELETE are honored by the home on an *authored-by* basis (the relaying network vouches `sender@net`; the home applies iff the sender authored the target or holds the moderation cap) and minted into the same order — not gated on a per-spoke msgid origin. Retention → strictest. `e2ee` bridges only pass-through MLS. Per-user attestation blocks without touching the manifest. *No transitivity — one hop from origin, loops structurally impossible, no shared state to resolve.*

[[s11-5]]
=== 11.5 Visibility interaction
Private/unlisted namespaces may bridge (root-signed only); their manifests are confidential — peers MUST NOT list their channels. `MANIFEST` notification to members on any audience change.

[[s11-6]]
=== 11.6 NETBLOCK
The operator's blocklist of remote networks — each entry `{network, private reason, added, actor}`. Blocking a network fires *all four effects (normative)*:

. Bridge *proposals are rejected*, both directions (`ERR BLOCKED`).
. Existing *manifests are severed* — members get `MANIFEST`, owners get `NETBLOCKED`.
. The network's *attestations are rejected* everywhere: AUTH, ingestion, invite redemption.
. Its *media is no longer fetched or mirrored*.

The block is *name-keyed*, so key rotation never evades it — evasion requires a new domain. Authority: the network key or the `netblock` cap. List visibility is configurable (`blocklist_visibility: operators|members|public`). Namespace owners cannot override a netblock but may keep narrower denylists (extension). Because federation is non-transitive, one block is total isolation — no propagation machinery exists or is needed.

*Operator acks (normative):* `NETBLOCK ADD` is acked by `NETBLOCKED <network> [:reason]` **carrying the reason** (so the operator's list reflects it without a `LIST` round-trip); `NETBLOCK REMOVE` is acked by `NETBLOCK-REMOVED <network>`. These are *distinct verbs* so a client applies a block (set) vs an unblock (delete) unambiguously — a bare reason-less `NETBLOCKED` for both would re-add an entry on removal.

[[s11-7]]
=== 11.7 Federated history backfill
Bridge peers use ordinary `HISTORY` over the bridge session. A request is served *iff all three hold*:

* the channel is in the mutually-acked manifest (invariant 3);
* the range is within the manifest's `history` flag — `from-epoch` serves nothing before the manifest's `created` timestamp (a cheap ULID compare);
* the origin's own retention still holds the data.

Backfilled events are verified like live traffic and stored under the negotiated policy (*not a retention loophole*); only the *compacted materialized view* is served (<<s12-1,§12.1>>) — backfill is not an undelete oracle.

*Bulk transfer.* When a served page exceeds ~200 events, the server answers with `STREAM ACCEPT <token>` instead of an inline `BATCH`; the requester pulls the serialized batch over the data plane — `BACKFILL <token>` (QUIC bidi) or `GET /backfill?t=<token>` (HTTP) — as newline-delimited event lines, folded exactly like an inline batch. The token is one-time; a failed pull is retried by re-issuing the `HISTORY` (a fresh token), so the server holds no cursor state.

*Reconnect.* `HISTORY after=<last stored>` per channel; expired ranges are marked `truncated` — never silent. Flipping `history=full` is a manifest amendment: version bump → re-ack → `MANIFEST` to members (the notification is built in).

*Lazy federated pull.* Bulk backfill is fetched *on client demand* — never eagerly on bridge-up; a federated scrollback nobody asks to see is never pulled:

. A local client's `HISTORY` for a forwardable channel runs out of local scrollback (a short page).
. The bridge asks the peer for that same window, *deduped per `(channel, before)` cursor*.
. The pulled lines feed back through ordinary bridged ingestion (invariants 2, 3), broadcast to members, and persist — the next page serves locally.

Pre-bridge scrollback requires `history=full` (`from-epoch` serves only post-manifest history) — which is why auto-federation always offers `history=full` (<<s11-10,§11.10>>).

[[s11-8]]
=== 11.8 Media across bridges
Referenced blobs *mirrored* (fetched over bridge data plane, BLAKE3-verified — substitution detectable). Rationale: clients only talk to home; hotlinking leaks reader IPs and breaks on origin outage. Bounded by manifest `media`; `none` renders unavailable-by-policy, never silent. Backfilled media rides `history`. Mirrors obey receiver retention *and receiver hash blocklist*.

*Mirror pull (concrete).* On ingesting a bridged message whose attachment URI has a _foreign_ origin:

. The receiver *records the reference locally* — its members are gated and can fetch — then pulls the blob over the *same authenticated bridge connection*, on a data-plane bidi stream: `MIRROR <requester-network> <b3-hash> <sig>` → `OK <mime> <len>` + bytes, or `ERR nosuch`.
. `sig` is the *requester network's* signing key over `hash‖requester‖origin` (domain-separated), so the request is _self-authenticating_: the origin serves iff a network it already federates with (a known peer key) proves control of that key — and it never needs to correlate the data-plane stream with a control-plane session (no origin↔member correlation).
. The receiver *verifies the returned bytes* hash to the requested `b3-hash` before storing (content addressing — the origin cannot substitute).
. Any failure — unknown requester, bad signature, absent blob — is the uniform `ERR nosuch` (invariant 1: presence never leaks).

The pull is eager (fired on ingest); a receiver with no live connection to the origin records the reference and skips the fetch until one exists.


[[s11-9]]
=== 11.9 Reports and federation

* A report always lands at the reporter's home network (<<s6-7,§6.7>>). For a bridged message, the home network can act *locally* without anyone's permission: local redaction of its replica (its storage, its rules — analogous to the receiver-side hash blocklist in <<s11-8,§11.8>>) and attestation-level blocking of the sender.
* The home network MAY additionally *forward* the report to the origin network over the bridge session (`REPORT-FORWARD <report-id> <msgid> <category> [:note]`, bridge-session-only verb). Forwarding strips the reporter's identity by default — the origin receives a network-attributed report ("test.example forwarded a harassment report against your msgid X"). Origin networks treat forwarded reports as net-scope, `unverified`-at-minimum input; they are free to ignore them, and chronic ignoring is what `NETBLOCK` is for.
* Report queues, resolutions, and holds NEVER replicate across bridges; there is no federated moderation state, only forwarded signals.

[[s11-10]]
=== 11.10 Auto-federation (on-demand bridging)

Federation can be established *without operator ceremony*: a local user referencing a foreign namespace — `FEDERATE <network>/<namespace>` (<<s6-6,§6.6>>), or a `weft://<network>/…` invite link whose network is not the user's home (<<s6-5,§6.5>>) — triggers the *home* network to establish the bridge itself. Outbound auto-establishment is governed by network configuration (`auto_bridge = open | off`): `off` disables the trigger (`FEDERATE` answers `UNSUPPORTED`) and leaves inbound bridging (<<s11-2,§11.2>>) unchanged.

*Reachability — the foreign side's consent.* The `federation` flag (`NS META <ns> federation :open`, <<s6-2,§6.2>>) is the master switch: it is *off by default*, and enabling it is always an explicit opt-in by the namespace owner — for _any_ visibility. With `federation` open, a namespace is _auto-federation-reachable_ iff **either** it is `public`, **or** the request carries a valid `invite` scoped to that namespace (`@invite=<id>` on `BRIDGE REQUEST`). The invite — not visibility — is the access control for a non-public namespace; it is validated *non-consuming* (a bridge is a network-level authorization that survives reconnects) against the ns-scope invite store (unexpired, not exhausted, not revoked).

* An invite never substitutes for the `federation` flag: a namespace with `federation: closed` is unreachable regardless of any invite.
* Anything else — absent, or `federation: closed`, or a non-public namespace with a missing/wrong/expired/exhausted/revoked invite — answers the uniform `NO-SUCH-TARGET` (invariant 1: neither a reachability probe nor a guessed invite learns anything an existence probe couldn't; only a *valid* invite, which already implies knowledge of the namespace, reveals it).
* A netblocked requester gets `BLOCKED` (<<s11-6,§11.6>>).
* Consent is structural: no request can compel a bridge — the foreign network offers its own signed manifest, or nothing.

*Triggers.*
. *Explicit* — `FEDERATE <network>/<namespace>` (<<s6-6,§6.6>>): a user asks their home network to go get a namespace it does not carry. This is deliberately a separate verb from `NS JOIN`: joining what already exists locally and causing an outbound dial have different failure surfaces (SSRF, netblock, dial failure, policy-off), and the dial should be explicit.
. *Invite redemption* — invite links embed both the namespace and the invite id (`weft://<net>/<ns>/i/<id>`, <<s6-5,§6.5>>), so a _foreign_ redeemer auto-federates to it by issuing `FEDERATE <net>/<ns>` with `@invite=<id>` (the reference client extracts `<id>` from a pasted link). This is exactly the path that unlocks an `unlisted`/`private` foreign namespace: the embedded invite is presented on the resulting `BRIDGE REQUEST`.

*Gates (home side), checked before any dial:* `auto_bridge` is `open` (else `UNSUPPORTED`, also returned for a self-network target); the target network is not netblocked (<<s11-6,§11.6>>, else `BLOCKED`); a *per-account cooldown* bounds trigger frequency (else `THROTTLED`). *TODO (confirm with owner):* the cooldown duration is implementation-chosen; no normative floor is stated.

*Flow* (home `H`, foreign `F`, namespace `N`):
. If a live `H↔F` bridge already covers `N`, reuse it — join, done.
. *Resolve `F`:* fetch `https://<F>/.well-known/weft` (<<s10-2,§10.2>>) for `F`'s network signing key. The fetch is TLS-verified and SSRF-guarded (below).
. *Dial:* connect over QUIC (ALPN `weft/1`) and open a bridge session — `AUTH BRIDGE`, proving `H`'s network key (<<s11-2,§11.2>>).
. *Request:* `BRIDGE REQUEST <N>` (<<s6-6,§6.6>>). If `N` is reachable, `F` signs `N`'s manifest (scope authority = `F`, <<s11-1,§11.1>>) *with `history=full`* — so the joiner can backfill the namespace's _existing_ scrollback (<<s11-7,§11.7>>), not just post-manifest traffic — and replies `BRIDGE PROPOSE`; else `NO-SUCH-TARGET`.
. *Accept:* `H` verifies the manifest against `F`'s key and auto-accepts (`BRIDGE ACCEPT`); the bridge is live, `N`'s channels mirror into `H` (<<s11-4,§11.4>>), and affected members get `MANIFEST` (<<s11-5,§11.5>>). The trigger's outcome is *asynchronous* — the `FEDERATE` ack precedes the landing `MANIFEST`.

*SSRF guard (normative — invariant 13).* The home network dials an address derived from a _user-supplied name_; that name MUST NOT be able to reach internal infrastructure. Every server-side fetch this flow performs — the well-known fetch and the QUIC dial — and every other server-side fetch of a user-influenced URL (e.g. the <<s13,§13>> unfurl proxy) MUST:

* resolve the host and classify *every* resolved address _before_ connecting, refusing non-public classes: loopback, private ranges (RFC 1918), CGNAT (`100.64/10`), link-local, ULA (`fc00::/7`), cloud-metadata addresses, and IPv4-mapped forms of these;
* strip URL userinfo before host extraction (`https://trusted@169.254.169.254/` must not smuggle an internal target);
* connect to the *verified IP* — no re-resolution between check and connect (no DNS-rebinding window);
* for HTTP fetches, re-run the guard on every redirect hop (≤5) and bound response size and time.

The guard MUST be implementable and testable as a pure address-classification function, separate from the dial path.

*Visibility.* An auto-established bridge is an ordinary bridge: announced via `MANIFEST` to affected members (<<s11-5,§11.5>>), visible on the network's federation surface, severable (`BRIDGE SEVER`) and blockable (`NETBLOCK`) like any other. Nothing about this path is silent.

[[s11-11]]
=== 11.11 The bridge as a command/event stream — homeserver authority

A bridge is *one network-authenticated session* between two servers (`AUTH BRIDGE`,
network key — <<s11-2,§11.2>>). Over it the two servers exchange exactly the two message
kinds the client protocol already has: *commands* (<<s4,§4>> requests, one direction) and
*events* (<<s7,§7>>, the async return). A server treats the bridge much like a client
connection, with two differences: it is authenticated at the *network* level, and a peer may
act on behalf of any of *its own* users by tagging a command `@as=<account>`.

* *Homeserver authority (normative).* Authority is anchored at the *network*, not the
  device. Network `F` proves control of its signing key at `AUTH BRIDGE`; it then *speaks
  for its own users* — as a linked IRC server does, and as a Matrix homeserver signs for
  its users. A user command `@as=<account> <§6 verb>` asserts that `F`'s local user
  `account` is acting; `H` reconstructs `account@F` and enforces the command against *`H`'s
  own grant store*. `F` may assert only its _own_ users (origin authority, <<s11-4,§11.4>>);
  it can never speak for `H`'s users or a third network's. Per-device command signing is
  deliberately *not* required: `F` is `alice`'s identity provider (it can reset her password
  / enroll devices), so a device signature buys nothing against a malicious `F` — the trust
  boundary is the network. The backstop for a misbehaving `F` is `NETBLOCK` (<<s11-6,§11.6>>).

* *Two kinds of command cross the bridge*, both plain <<s4,§4>> lines — no wrapper frame:
  ** *Network commands* — the network itself acts, no actor tag: the manifest lifecycle
     (`BRIDGE PROPOSE`/`ACCEPT`/`ADD`/`REMOVE`/`SEVER`/`REQUEST`), `REPORT-FORWARD`, and the
     media-plane `MIRROR`. Authorized by the network key / the <<s11-3,§11.3>> ladder.
  ** *User commands* — `@as=<account> <ordinary §6 command>`. This one form carries
     *everything* a federated user does: content (`MSG`/`EDIT`/`DELETE`/`REACT`),
     capabilities & roles (`GRANT`/`REVOKE`/`ROLE …`/`CAPS`), moderation
     (`MUTE`/`BAN`/`KICK`/`REPORT`/`REPORTS …`), channel & namespace admin
     (`CHANNEL …`/`NS …`/`INVITE …`), social (`FRIEND …`/`CALL …`/`GROUP …`), and `HISTORY`.

* *Events are the only return (normative).* No command has a synchronous reply frame; every
  effect is an event. A *labelled* command is acked by the event carrying the same `label`
  back — the <<s3-5,§3.5>> rule, extended to the bridge: `@label=L GRANT …` → `@label=L
  TOKEN …`; `@label=L MSG …` → the home-minted `@label=L MESSAGE …`. The sending server
  remembers `label → its user's session`; a returning labelled event is delivered to that
  session. An event may fan out to several peer networks at once (its *audience*,
  <<s11-12,§11.12>>); the label rides *only* the copy to the origin network — every other
  network in the audience gets the event unlabelled.

* *IP non-exposure (MUST).* All cross-network traffic is server-to-server over the one
  bridge. A user never connects to `H`; `@as` carries an account, never an address. `H` only
  ever sees `F`'s server address. No verb or event may reveal a user's IP to a foreign network.

* *Enforcement.* `H` verifies `F` (network key), attributes each `@as` command to the vouched
  `account@F`, and checks it against `H`'s grant store exactly as for a local actor
  (capability checks precede side effects, <<s10-4,§10.4>>). Operator / namespace-owner
  authority is *local-only* — never satisfied by a foreign actor; a federated user's power on
  `H` is exactly what `H` granted `account@F`.

[[s11-12]]
=== 11.12 Home-authoritative content — channels & groups

A channel or group with members on more than one network has a single *home*: for a
channel, the network that owns its namespace; for a group DM, the creator's network. The
home is the *sole ULID writer* (<<s9-1,§9.1>>) — it mints every message into the single total
order, and every other member network *mirrors* that order (a channel spoke runs a *replica*
holding a bounded tail of pending local posts). A remote member's `MSG`/`EDIT`/`DELETE`/`REACT`
is *relayed to the home to be minted* — a spoke never mints shared content itself. This is
what makes a cross-network total order well-defined, and — because the home is the single
origin — what lets a post from one spoke reach _another_ spoke at all (one hop from the home;
a spoke→spoke forward would be the forbidden transitivity of <<s11-4,§11.4>>).

The mechanism is *identical for channels and groups*; the only difference is an event's
*audience* — the set of networks a home-minted event fans out to:

* *Channel* → the channel's *manifest-sharers* (peers that carry it in the acked manifest,
  <<s11-1,§11.1>>). The fan-out is the ordinary event mirror (<<s11-4,§11.4>>).
* *Group* → the group's *member networks* (from the roster). A group has no manifest or
  replica, so the home fans each event out *explicitly* to every member network.

*The up-leg.* A member on a spoke posts `@label=L MSG <target> :hi`. The spoke renders it
optimistically (pending, keyed by `L`), mints a *bridge label* `B-<home>-<ULID>`, remembers
`B → the posting session`, and sends `@as=<account> @label=B MSG <target> :hi` to the home.
`EDIT`/`DELETE`/`REACT` relay the same way, keyed on the target msgid; the home resolves each
target's scope + author and applies it iff `<account>` authored it (or holds the moderation
cap, <<s11-4,§11.4>>).

*The down-leg.* The home mints `msgid = H/<ULID>`, delivers to its own members, and fans the
home-origin `MESSAGE` out to the audience. On the copy to the *poster's* network only, it
carries `@label=B`; the poster's spoke matches `B` back to the waiting session and delivers
the minted message as that session's own *labelled* copy — the ordinary <<s3-5,§3.5>> ack — so
the client reconciles by `label`, exactly like a local post. Every other network's copy is
unlabelled. `B` lives on the up-leg and the one return copy and nowhere else: never persisted,
never seen by a client. Mutations fan out as `EDITED`/`DELETED`/`REACTION` events the same way.

*Membership.* A channel's membership is carried by the manifest (<<s11-1,§11.1>>) + the
`MEMBER` mirror. A group's membership is a roster the home keeps authoritative across
networks with a `GROUP-ROSTER` event (<<s11-15,§11.15>>): the full member list, applied as an
add/remove diff by each receiver (parting any removed local member), sent on create and every
change — the group analog of a channel's `MANIFEST`.

*Backfill (recovery).* A member catching up sends `@as=<account> HISTORY <target>
[after=<cursor>]` (`after` = its newest local msgid, or absent for the whole history). The
home replays the messages after the cursor as ordinary `MESSAGE` events over the bridge, which
the member ingests idempotently (dedup on msgid). A non-member / unmanifested network gets
nothing (anti-enumeration, <<s11-1,§11.1>>). This is the ordinary <<s6-4,§6.4>> `HISTORY` verb,
run `@as` over the bridge — there is no separate backfill verb. Live home→spoke delivery
always rides the fan-out above; `HISTORY` is the recovery path only.

*Attachments.* A cross-network message carrying a `weft-media://` attachment triggers a
mirror pull of the blob from its *origin* network (<<s11-8,§11.8>>), so local members can fetch it.

[NOTE]
.Staying fast (non-normative rationale)
====
Home-authority adds a round-trip only to a cross-network post's _finalization_, not to its
appearance or to reads: (a) the spoke renders the poster's own message *optimistically* at
once and reconciles it to the home-minted copy by matching the `label`; (b) `HISTORY` and
scrollback are served from the *local replica* with no round-trip; (c) the up-leg is
fire-and-forget and pipelined, so posts do not head-of-line-block on confirmation; (d) a
member whose network _is_ the home mints locally with no relay at all — the common case.
See `docs/architecture/home-authoritative-channels.md`.
====

=== 11.13 The message flow between two servers

NOTE: The walkthroughs below show channels by *vanity* (`#gaming/general`) for readability; on the wire each is the ULID form `#<ns-id>/<chan-id>` (<<s5-3,§5.3>>).

`alice@s.example` posts to `#gaming/general`, whose home is `h.example`. Both legs ride the
one authenticated bridge (<<s11-2,§11.2>>) — alice never connects to the home.

----
   NETWORK  S  (spoke — alice is a member)          NETWORK  H  (home — owns #ns/chan)
 ┌────────────────────────────────────────┐       ┌────────────────────────────────────────┐
 │ alice: @label=L MSG #ns/chan :hi        │       │                                        │
 │   │                                     │       │                                        │
 │   ▼  (1) optimistic echo — show "hi"    │       │                                        │
 │       now, pending, keyed by label L    │       │                                        │
 │   │   (S mints bridge label B, B→alice) │       │                                        │
 │   ▼   up-leg: an @as command over bridge │ ────▶ │ (2) mint msgid = H/<ULID>              │
 │  @as=alice;label=B MSG #ns/chan :hi     │       │     single ULID writer = the order     │
 │                                         │       │   │                                    │
 │                                         │       │   ├─▶ (3) deliver to H's local members  │
 │                                         │       │   │      (unlabelled — not the poster)  │
 │  (5) match label B → alice's session,   │ ◀──── │ (4) fan out to the audience; the copy  │
 │      deliver as her @label=L echo,      │       │     to the poster's network carries    │
 │      she reconciles by label            │       │     @label=B, every other copy omits it │
 │                                         │       │  @msgid=H/<ULID>;label=B MESSAGE … :hi  │
 └────────────────────────────────────────┘       └────────────────────────────────────────┘
        └───────── one authenticated bridge session (AUTH BRIDGE, network key) ─────────┘

 Home-network member:  MSG #ns/chan :hi → H mints locally + delivers.  No relay, no wait.
 Reads (HISTORY):      served from S's local replica.  No round-trip to H.
 Audience:             channel = manifest-sharers (the event mirror); group = member networks.
 Recovery:             on reconnect S sends @as HISTORY; H replays missed messages as MESSAGE.
----

On the wire:

----
 client → S   @label=L1;fmt=md MSG #gaming/general :hi everyone
              (S renders it at once — pending, keyed by label L1; S mints bridge label
               B1 = B-h.example-01…, remembers B1 → this session)

 S → H        up-leg — an @as command over the one bridge (fire-and-forget):
              @as=alice;label=B1;fmt=md MSG #gaming/general :hi everyone

 H            mints  msgid = h.example/01ARZ3NDEKTSV4RRFFQ69G5FAV, delivers to H's locals,
              then fans the home-origin MESSAGE out to the audience

 H → S        down-leg — the copy to the poster's network carries @label=B1; every other
              network's copy omits it:
              @msgid=h.example/01ARZ3NDEKTSV4RRFFQ69G5FAV;label=B1;fmt=md MESSAGE #gaming/general alice@s.example :hi everyone

 S → client   S matches label B1 → alice's session, delivers it as her own @label=L1 MESSAGE;
              her client reconciles the pending copy by label L1
----

Recovery, after `S` was unreachable — `S` pulls with `HISTORY`, `H` replays as ordinary
`MESSAGE` events (idempotent on msgid; live delivery always rides the fan-out above):

----
 S → H   @as=alice HISTORY #gaming/general after=h.example/01ARZ3NDEKTSV4RRFFQ69G5FAV
 H → S   @msgid=h.example/01ARZ3NDEKTSV4RRFFQ69G5FAW MESSAGE #gaming/general bob@h.example :hey
----

*Availability.* Reads are served from the replica even while the home is unreachable. Posts
are queued in a bounded outbox (invariant 6 backpressure) and stay visible as _pending_; on
the home's recovery the spoke replays them (`@as HISTORY`) and they mint into order — nothing
is lost. If the home is permanently gone the replica is frozen read-only at its last-mirrored
state.

=== 11.14 Federation command reference

This is the *home↔spoke* command surface — the federation counterpart to the client↔server
reference (<<s6,§6>>). Implement it to be a server that federates. It has two kinds of entry:

* *Network commands* — spoken by the network itself (no actor tag): bridge control, media
  mirror, report forwarding, and the operator's `NETBLOCK`.
* *User commands* — an ordinary <<s6,§6>> verb a federated user runs on the home, tagged
  `@as=<account>` (<<s11-11,§11.11>>). These appear in *both* references (client→own server in
  <<s6,§6>>; own server→home here); the home enforces each against its own grants for
  `account@F`, and *content* verbs mint home-authoritatively (<<s11-12,§11.12>>). There is no
  separate content or backfill verb — `MSG`/`EDIT`/`HISTORY`/… *are* the wire.

Non-normative index; normative syntax lives in the cited subsection.

_Direction:_ `S→H` = spoke → home (a user's `@as` command) · `H→S` = home → spokes ·
`↔` = either peer · `P↔P` = peer ↔ peer · `mesh` = gossiped among all member networks ·
`client→home` = a user to their own server · `local (op)` = an operator command on its own server.

[[s11-15]]
=== 11.15 Federation event reference

This is the *home↔spoke* event surface — the federation counterpart to <<s7,§7>>. Events are
the *only* return over a bridge (<<s11-11,§11.11>>). Some are *federation-only* — the bridge
handshake, `MANIFEST`/`NETBLOCKED`, backfill framing. The rest are ordinary <<s7,§7>> events

[[s12]]
== 12. History, Retention & Compaction (server duties)

* Retention enforced by the storing network; purge tasks honor policy; tombstones persist in `retained`/`permanent`.
* Clients get `HISTORY` only from their *own* network (trust cornerstone). Origin = authoritative copy; replicas bounded by negotiated policy.
* Media blobs refcounted against referencing events.

[[s12-1]]
=== 12.1 Message compaction (new)

Two regimes, one principle: *live is event-sourced, at-rest is materialized.*

*Live path (unchanged):* real-time subscribers receive every event as it happens — `MESSAGE`, then `EDITED` per edit, `REACTION` per add/remove, `DELETED`. Clients need the increments for UI.

*Audit window:* intermediate events (superseded edit bodies, cancelled reaction pairs) are retained verbatim for `compact-after:<dur>` (network config, default *24 h*; settable per channel by `policy` cap holders) — the moderation window in which "what did it say before the edit" is answerable.

*Compaction (after the window):* the stored log per channel is rewritten:
* An edited message → *original event + final edit only*; intermediate edit bodies dropped. The count survives.
* Reaction add/remove pairs that cancel → dropped; surviving reactions → per-emoji summary rows.
* A deleted message → *tombstone only* (the `DELETED` event); content gone per retention rules, as before.
* Replies/threads unaffected (structural tags live on surviving events).

*Wire form (batches):* `HISTORY`/backfill responses carry the compacted materialization and mark it `compacted` on `BATCH END`:
* One `MESSAGE` per surviving message with final body + `edited=<count>` + `edited-at=<ms>` tags — no `EDITED` chains in batches.
* `REACTIONS <#ns-id/chan-id> <msgid> <emoji> <count>` summary events (`by=` lists the first ≤20 actors; the count is authoritative) — no add/remove ping-pong.
* `DELETED` tombstones as-is.

*Retention holds (reporting interplay).* Filing a `verified` report places a hold on the reported event and its context (RECOMMENDED: ±25 surrounding events in the channel):

* Held events are exempt from *both* compaction and retention purge — including in `retained:<d>` channels, and including pre-edit bodies still inside the audit window at filing time — until the report resolves plus a 7-day grace.
* Holds are *invisible* to ordinary members: no protocol surface reveals that a message is under report.
* `ephemeral` channels store nothing, so nothing can be held (hence `unverified`); `e2ee` holds preserve ciphertext blobs only.

*Effects elsewhere:*
* Backfill (<<s11-7,§11.7>>) automatically benefits: bridge catch-up transfers shrink by the edit/reaction churn factor, and the existing "materialized view only" rule becomes precisely specified rather than implied.
* `MARK`/read logic unaffected (markers reference surviving msgids; a marker on a compacted-away edit event resolves to its `edit-of` root).
* E2EE channels: the server cannot compact ciphertext (it can't see event relations inside); e2ee compaction is client-side during device sync — normative non-goal for servers.
* Moderation implication, stated honestly: after the audit window, pre-edit content is *gone on this network*. Networks wanting longer audit trails raise `compact-after`; the protocol default favors the "edits eventually really disappear" privacy expectation.

[[s13]]
== 13. Media

*Model.* Media is content-addressed: a blob's identity is its BLAKE3 hash, referenced as `weft-media://<origin-network>/<b3-hash>` with `{mime, bytes, w, h, duration?}` metadata; identical bytes collapse to one blob (dedup by construction). Posting: `attach.N=` tags (≤10), `attach-meta=`; bare media = empty trailing + tags. A reference MAY carry a trailing `#<w>x<h>` size hint (`weft-media://net/<b3-hash>#800x600`, from the uploader's known dimensions) so a renderer reserves exact space before the bytes load; the suffix is *not* part of the content address — all gating, refcounting and fetches strip it and key on `<origin>/<hash>` only. Fetching is *home-network only* — a client never fetches from a foreign network (that is what <<s11-8,§11.8>> mirroring is for). E2EE: the client encrypts before upload; no server thumbnails; host-blindness extends to attachments.

*Upload.* `STREAM OFFER media <mime> <bytes>` (checks `attach` + size config; RECOMMENDED 25 MiB image / 500 MiB video) → `STREAM ACCEPT <token>` → data-plane transfer → the server hashes and stores. The server probes image dimensions and derives a small thumbnail as its own auto-referenced blob.

*Transfer surfaces (one blob store, three doors).* All share the `STREAM OFFER` → `STREAM ACCEPT <token>` grant flow:

. *QUIC data-plane bidi framing* — `PUT <upload-token>`, `GET <bearer> <hash> [range]`, and the <<s11-8,§11.8>> `MIRROR <requester-net> <hash> <sig>`.
. *HTTP* — `POST /media` (upload; OFFER token or session bearer) and `GET /media/<hash>?t=<bearer>` (Range-capable, so video is ranged/segmented fetch; live A/V is WEFT-RT, <<s16,§16>>).
. *`BACKFILL <token>`* — the bulk pull for large history pages (<<s11-7,§11.7>>).

*Fetch authorization.* Right after auth the server pushes a per-session *bearer* as a `MEDIA TOKEN` event (<<s7-1,§7.1>>); fetches are membership-gated by it. A bad bearer, a non-member fetch, and an absent blob are *one uniform not-found* (invariant 1).

*Bookkeeping.* Blobs are refcounted against the events (and avatars/emoji) that reference them; orphans are collected after a grace period (<<s12,§12>>).

*Moderation.* Hash-level blocking (`MEDIA BLOCK`, <<s6-6,§6.6>>): blocking deletes the blob + its thumbnail and rejects re-upload _and_ mirror of the same bytes — content = identity, so re-uploads are dead on arrival.

*Link-preview (unfurl) proxy.* Clients never fetch third-party URLs (<<s9-4,§9.4>>); the server fetches on their behalf, so the origin host never sees the viewer:

* `GET /unfurl?url=<href>&t=<bearer>` — the page's OpenGraph/meta preview as JSON (`url`, `title`, `description`, `image`, `site_name`).
* `GET /unfurl/image?url=<href>&t=<bearer>` — proxies the preview image bytes.

Both require the same session bearer as `/media` (never an open proxy) and are *SSRF-guarded per <<s11-10,§11.10>> / invariant 13*: resolve → classify every address → pin the verified IP; re-check each redirect hop (≤5); strip userinfo. Fetches are size- and time-bounded; non-HTML/non-image results yield an empty preview. A network MAY disable unfurling.

[[s14]]
== 14. E2EE

Channel mode `e2ee` = *MLS (RFC 9420)* group keying; server = blind Delivery Service. Consequences (enforced + surfaced): no server search, no server embeds, no server thumbnails, no server compaction; history = client-mediated device sync. Retention enum makes "encrypted but server-readable" unrepresentable. Policy transitions to/from `e2ee` need an empty channel or explicit `purge`. Recovery (<<s2-4,§2.4>>) never restores e2ee history.

(2) *`edit-own`/`delete-own` are not capabilities* — acting on your own message is authorship-gated and always allowed (they were only ever error-context strings, never enforced caps), so they're gone from the permission editors. (3) *`delete-any` is now enforced* — a channel `DELETE` by a non-author succeeds iff the actor holds `delete-any` at the channel (moderator delete; the tombstone is attributed to them). Previously the cap existed but the delete path checked only authorship. (4) *Join/part + `view-gated`/`posting` flags* pushed on join as label-less `CHANMETA` so a client opens settings with accurate state; moderation (`MUTE`/`BAN`/`KICK`) and permission changes surface in Server Settings / capability state, never as channel system lines. Membership system lines carry a msgid and are deletable by their subject or a `delete-any` moderator. → <<s6-5,§6.5>>, <<s6-7,§6.7>>.
* _Operator authority is network-level only (not per-namespace):_ `actor_has_cap`'s operator short-circuit now fires only for **non-namespace** scopes — `*` and top-level network channels. An operator is no longer the implicit admin/owner of a *user's* namespace (`ns:<name>` / `#ns/chan`); there they're an ordinary member. Cross-namespace operator intervention (takeover, freeze, delete, moderation) is an out-of-band act through the **web admin panel** (store-direct, bypasses the cap system), and namespace recovery **rung 3** stays network-key-signed — so neither depends on the removed short-circuit. Namespace owners still hold every cap within their own namespace (the owner short-circuit is unchanged). Rationale: "admin" is a network-operations role, not day-to-day control of servers other people own. Client-side this is surfaced as a **Staff** badge (operators) distinct from the owner crown (shown only in Server Settings), and members' names render in their highest role's color. `NS LEAVE` is now client-wired (the owner can't leave — transfer or delete instead). → <<s2-4,§2.4>>, <<s6-7,§6.7>>, <<s10-4,§10.4>>.
* _Welcome channel:_ a namespace can designate a channel that greets new members. `NS META <ns> welcome :<#ns/chan>` (ns-admin; empty clears) sets `NamespaceRecord.welcome_channel` (store, migration 0044, mem+PG); `NS-META` carries a `welcome=` tag. On a member's **first** namespace join — via `NS JOIN`, `JOIN #ns/chan`, or invite redeem — the server posts a persistent `system=welcome` message (a channel-actor `Cmd::Welcome`) to that channel, so it rides `HISTORY` like any join/part line. Re-joins/auto-rejoins don't re-fire it. → <<s6-2,§6.2>>.
* _Mentions & pings:_ roles carry a `pingable=` flag and there is a `ping-everyone` capability, so `@everyone`/`@here` and `@<pingable-role>` are the model's notification triggers (<<s6-3,§6.3>>). Shipped: the `pingable=` role param (command + `ROLE` event + store, mem+PG), the `ping-everyone` cap, and client rendering (highlight + mention count, role-colored pills, composer autocomplete for `@everyone`/`@here`/single-word pingable roles). The mention count stays a body-text heuristic (no structured mention field). Staged follow-up: server-authoritative gating of `ping-everyone` on the pushed `UNREAD-COUNTS` mention tally — today the tally counts `@everyone`/`@here` regardless of the sender's cap; the un-fakeable gate needs the mention summary computed at append with the sender's caps in view. → <<s6-3,§6.3>>, <<s6-5,§6.5>>.
* _Rung 3 is immediate (supersedes the M4-6 30-day window):_ a delay defends against a _lost key_, not a _live adversary_ — the window's veto belonged to exactly the party being removed. What is given up is stated plainly: the delay + veto half of invariant 9, and a compromised network key can now seize a namespace instantly — accepted because an operator already hosts the data and holds every cap at `*`. What is kept carries the accountability: network-key authorization, the announcement, and the permanent operator-initiated `root-history` mark; e2ee remains the real boundary (invariant 8). → <<s2-4,§2.4>>.

=== v0.13 — ULID identity + email registration & password reset

* _v0.13 (wire- and storage-breaking)._ Two independent changes.
+
**(1) ULID identity for namespaces, roles, and channels.** A namespace, role, and channel each gain an immutable *ULID*, minted once at creation; their former names become mutable *vanity labels*, per-network-unique and lockable (<<s5-3,§5.3>>). The wire and every signed scope now carry the ULID: `ns:<ns-id>`, `#<ns-id>/<chan-id>` (both segments ULIDs), `#<chan-id>` for a top-level channel, and role commands/events reference the role ULID. `NS CREATE` / `CHANNEL CREATE` / `ROLE CREATE` take a *vanity* and the server mints the id; `NS-META` carries `id` + a `vanity=` tag, `CHANNEL-*` events carry the vanity alongside the id-name, and `ROLE`/`ROLE-MEMBER` carry role ids. Federation *pins the ULID* (`<network>/<ns-id>`); DISCOVER, invite links, and `FEDERATE` resolve vanity→ULID at the boundary and pin the id. *Why:* a name that _is_ the identity can't be renamed (it's baked into signed tokens, grants, channel names, and federation addressing) and can't be moderated independently — the ULID makes renames free and vanity names lockable, exactly as the earlier account name→ULID move did for accounts (<<s10-1,§10.1>>). Capability-token scope strings carry the ULID (no crypto structural change); old name-scope tokens become inert and re-mint from migrated grant records on next auth. → <<s2-1,§2.1>>, <<s5-3,§5.3>>, <<s6-2,§6.2>>, <<s6-3,§6.3>>, <<s6-5,§6.5>>, <<s7-4,§7.4>>, <<s10-4,§10.4>>, <<s11-10,§11.10>>. Full plan: `docs/architecture/ulid-identity-v0.13.md`.
+
**(3) A bridged realm is a network; account grammar widened.** A foreign realm reached through a bridge (Matrix, Discord, …) is modeled as a *network*, not as a set of local puppet accounts: a bridged user is `alice@matrix.org`, the bridge *mints their msgids* under the realm (`matrix.org/<ulid>`), and weftd ingests them through the ordinary federated path — same origin-authority check (invariant 2), same one-hop forwarding, same `ingest_record`. A replica channel is therefore multi-origin exactly as a peered channel is, and "did this event come from the bridge?" is answered by `msgid.origin`, with no bridge-specific tag. *Why:* the alternative carried a `foreign=` display tag beside a locally-minted event, which (a) duplicated what `user@network` already says and (b) papered over a real defect — the local puppet name was derived lossily, so two distinct foreign users could collide onto one WEFT identity. Accounts therefore admit `=` and `+` (<<s2-3,§2.3>>) so an adapter can carry a Matrix localpart verbatim; the adapter owns the foreign→WEFT mapping and must keep it injective, and weftd enforces only that a bridge's `@as` and `@msgid` both name the realm it speaks for. → <<s2-3,§2.3>>, <<s11-4,§11.4>>. Framework: `docs/architecture/foreign-bridge-framework.md`.

**(2) Email registration + password reset.** `REGISTER` takes an optional contact email (`REGISTER <account> [<email>] :<password>`); a network MAY set `require_email` to make it mandatory for native clients (verify-later: the account works immediately, `VERIFY EMAIL` confirms whenever). The email is unique per account and powers reset. `RESET REQUEST <email>` mails a one-time code — answered with a *uniform* `RESET-SENT` whether or not the email is known (anti-enumeration) — and `RESET CONFIRM <email> <code> :<new-password>` sets the new password (`RESET-DONE`; the session stays unauthenticated, the client then `AUTH`s). Both reset verbs are valid only while UNAUTHED. The WEFT-IRC gateway is exempt from `require_email` (it auto-registers emailless accounts, which can't reset). `require_email` requires a configured mailer (<<s10-5,§10.5>>). → <<s6-1,§6.1>>, <<s7-1,§7.1>>, <<s10-5,§10.5>>.

=== Post-v0.13 clarifications

* _Line limit 8 KiB → *32 KiB*; plugin payloads moved off tags._ <<s12,§12>>'s plugin surface carries base64-CBOR *documents* on the control plane — a provider's action catalog, an SDUI view, a form submission — and they were riding `@tag=` values, which <<s4,§4>> caps at 1024 B. The reference bridge's seven action declarations came to ~1.4 KB and the session died with `tag "reg" value exceeds 1024 bytes`; the aggregate `PLUGIN-MANIFEST` (every registered provider) would have been worse. Two changes, because they answer different questions. *Where:* every plugin payload now rides the **trailing** — a tag value is metadata, and 1024 B is what enforces that; the trailing is the slot for an opaque blob. *How much:* the line limit is raised to 32 KiB, since one line must hold an aggregate catalog and 8 KiB left too little headroom. The tag cap is deliberately unchanged. Cost is bounded per-connection buffering (`32 KiB × max_connections`); the IRC gateway keeps its own 8 KiB reader cap, which was never the same constant. → <<s4,§4>>, <<s12,§12>>.
* _Moderation names a *member*, not an account._ `MUTE`/`UNMUTE`/`BAN`/`UNBAN`/`KICK` and the `MODERATED` event took a bare `<account>`, which cannot express a member who lives on another network — so a **bridged** member (a Matrix user in a projected or consumed namespace) was unmoderatable *by construction*: the line did not parse. They now take a `<member>` (bare, or `<account>@<network>`), the form namespace rosters have carried since v0.12. Two enforcement points come with it: the deny-list is checked where bridged traffic **enters** (a banned member's relayed messages are refused on ingest, as a NETBLOCKed network's are — previously no ingest path consulted it at all, so a ban would have been decorative), and the act SHOULD be relayed to the realm to be applied foreign-side, with an explicit rule that the relay's failure never undoes the local deny. *Why:* a moderator's authority is over the room, and half the room being unreachable to it is not a policy — it is a missing parameter. → <<s6-7,§6.7>>, <<s7,§7>>.
* _NETBLOCK acks disambiguated._ `NETBLOCK ADD` and `REMOVE` both used to echo a reason-less `NETBLOCKED <network>`, so a client couldn't tell block from unblock — applying either as a set meant a `REMOVE` *re-added* the entry (reconciled only via a `LIST` refresh). Now `ADD`/`LIST` echo `NETBLOCKED <network> [:reason]` **with the reason** and `REMOVE` echoes a distinct **`NETBLOCK-REMOVED <network>`**, so a client sets on the former and deletes on the latter — no refresh workaround. → <<s11-6,§11.6>>, <<s7,§7>>.

== Appendix B — Reference-implementation notes (non-normative)

Where the reference implementation (weftd) keeps things — useful to contributors, meaningless for wire conformance. *Renaming anything here never changes the protocol.*

* *Storage.* PostgreSQL behind storage traits (an in-memory backend runs the same contract tests). Notable migrations: `0009` moderation deny-list + the channel `restricted` flag, `0010` pins, `0011` persistent membership, `0020` media blocklist, `0026` account `operator` flag, `0027` emoji, `0031` thread names. Search is case-insensitive substring on both backends for identical semantics (a Postgres `tsvector` upgrade is a noted refinement); unread counts reuse the event rows (no migration).
* *Operators.* Operator authority is a per-account store flag managed by a `weftd admin` CLI (`create`/`grant`/`revoke`/`list`, direct-to-Postgres — the bootstrap admin is created this way); the config `operators` list survives only as a deprecated seed. The check reads the store live, so changes need no restart.
* *Invites.* Implemented as server-side id + counter records; <<s6-5,§6.5>>'s offline-verifiable unbound-token object is the design target (a federation concern).
* *Mail.* `VERIFY EMAIL` delivery is SMTP configured in weftd (`[smtp]`); an unconfigured development server records the claim and logs the code.
* *Unfurl.* Toggle `[unfurl] enabled` (default on). The HTML meta extractor is a pure, dependency-free parser; a permissive CORS layer fronts `/media` and `/unfurl` (desktop-webview uploads send non-simple preflights).
* *Constants.* History→STREAM threshold *200* events (`HISTORY_STREAM_THRESHOLD`); report-hold context radius *25* (`HOLD_RADIUS`); rung-3 delay *0* (`RECOVERY_DELAY_RUNG3_SECS`) — applied inline rather than parked with an already-elapsed ETA, which would leave the namespace in the abuser's hands until the next maintenance tick.
* *IRC gateway shipped subset.* Registration (`NICK`/`USER`/`PASS` → `HELLO` + `AUTH`, auto-`REGISTER` on first `AUTH-FAILED`; a ≥12 B `PASS` is the WEFT password), `JOIN`/`PART` incl. `#ns/chan`, `PRIVMSG`/`NOTICE` ↔ `MSG` (bare nick = DM; own echo suppressed), `NAMES` (fills from observed joins), `LIST` ← `DISCOVER`, `PING`/`QUIT`, MOTD; edits/deletes/reactions degraded to text. Deferred: SASL, IRCv3 tags, chathistory, TAGMSG, MODE/TOPIC/KICK projection, WEFT↔512 B line splitting, the e2ee-invisible treatment. Enabled by `[listen] irc` (plaintext; TLS termination is the operator's).
